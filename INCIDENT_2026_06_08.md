# Incidente 2026-06-08 — Cascada de bugs y fixes definitivos

Resumen del incidente del 8-jun en n8n B y los fixes aplicados.

## Síntoma observado

- Cobertura del Audit ATC cayó de 99.3% (5-jun 19:30) a 3.9% (8-jun 19:30).
- 220 leads de Discord faltaron procesarse en PCL B en una ventana de 12h.
- Discord seguía emitiendo leads OK pero PCL B no los recibía.

## Cronología

| Hora (Lima) | Evento |
|---|---|
| Dom 03:00 (08:00 UTC) | Primer cron automático del `Zombie Cleanup Auto B` (lo creé el 5-jun). Tenía >3 días de zombies acumulados. |
| 08:42 | **TODOS los crons de n8n B se detienen simultáneamente** (Bridge, LeadAsesor, ErrorNotifier). El scheduler de cron quedó muerto. Los webhooks SÍ siguieron respondiendo. |
| 19:30 | Audit ATC reporta 3.9% cobertura. |
| 20:00–22:00 | Diagnóstico + reposteo manual de 241 leads en grupos de 10 cada 30s con bypass Wait. |

## Causa raíz (mi error, no infra)

1. **Cleanup B sin cap**: la primera corrida del Cleanup B borró miles de zombies en bucle (sin límite por corrida), saturando el worker o el connection pool de Postgres. El scheduler de cron quedó degradado y dejó de disparar.
2. **Bridge B confiaba solo en cursors**: al reanudar después de un atasco, los cursors pueden quedar stale (apuntando a hace horas/días). Sin filtro de timestamp en el msg propio, el Bridge envió leads viejos al webhook.

## Fixes definitivos aplicados

### 1. `Zombie Cleanup Auto B` y `A` con cap

```js
const MAX_DELETES_PER_RUN = 500;
const MAX_PASSES = 5;
const CHUNK_SIZE = 3;
const SLEEP_BETWEEN_PASSES_MS = 10000;
```

Antes era ilimitado, 10 passes, 5 chunks paralelos, 2s entre passes. Ahora una corrida tarda <4 min máximo, no satura.

### 2. Bridge B con `AGE FILTER`

En `Bridge Extract`, justo después de filtrar bot messages:

```js
const MAX_AGE_MS = 2 * 60 * 60 * 1000;
const msgTimestamp = new Date(msg.timestamp).getTime();
if (Date.now() - msgTimestamp > MAX_AGE_MS) {
  if (msg.id > channelMaxMsgId[r.channelId]) channelMaxMsgId[r.channelId] = msg.id;
  continue;
}
```

Rechaza Discord msgs >2h ANTES de enviarlos al webhook. Independiente del cursor. Previene que después de cualquier reset, atasco o reload se envíen leads viejos a clientes.

### 3. PCL B con `If Discord Reciente` (defensa en profundidad)

Insertado entre `Leads` y `Wait` (y entre `Recovery` y `Wait1`):

```
Leads → If Discord Reciente → [true: Wait, false: No Op Stale Discord]
Recovery → If Discord Reciente → [true: Wait1, false: No Op Stale Discord]
```

Si el `AGE FILTER` del Bridge falla por bug futuro, PCL B sigue protegido. Los webhooks viejos terminan en No Op en segundos, no entran al Wait 10min ni saturan la cola.

## Lecciones

- **Cleanup workflows necesitan cap duro por corrida**. Sin cap, la primera corrida tras X tiempo de acumulación puede colapsar al scheduler.
- **No confiar solo en cursors stale-resistant**. Validar también por timestamp del propio dato. Defensa en profundidad.
- **Si el cron scheduler muere mientras los webhooks viven, la cola interna de webhook events de n8n sigue acumulando mensajes y disparando execs**. Desactivar el workflow trigger no detiene la cola — solo rechaza nuevos POSTs. La cola pendiente sigue procesándose por horas.
- **AGE FILTER es más robusto que cursor**: el cursor depende de staticData (puede corromperse, perderse en restart, fallar en init). El timestamp del msg viene del propio Discord y es inmutable.
